# Conventions

These are common OutSystems 11 defaults. Adjust them to the team's standard; Claude follows whatever this file says.

## Naming

| Element | Convention | Example |
|---|---|---|
| Module | PascalCase, layer suffix | `Sales_CS`, `Payments_IS`, `Sales_Th` |
| Entity | Singular PascalCase | `Customer`, `OrderLine` |
| Static entity | Singular PascalCase | `OrderStatus` |
| Attribute | PascalCase. Foreign keys are `<Entity>Id` | `Name`, `CustomerId` |
| Boolean attribute | `Is…` / `Has…` | `IsActive`, `HasAttachments` |
| Structure | PascalCase, describing the shape | `CustomerSummary`, `OrderRequest` |
| Server action (reusable, under Logic) | `<Entity>_<Verb>[<Qualifier>]`, see [Action names](#action-names) | `Customer_GetById`, `Order_CreateOrUpdate`, `Order_GetNewest` |
| Client action (reusable, under Logic) | `<Entity>_<Verb>[<Qualifier>]`, see [Action names](#action-names) | `Minutes_Format`, `Date_GetWeekStart` |
| Screen / block action bound to an event | `<Event>_<Target>`, see [Action names](#action-names) | `OnClick_SaveButton`, `OnChange_HoursDropdown`, `OnAfterFetch_GetKPIs` |
| Screen / block helper action (not bound to an event) | Verb + noun | `OpenDayEditor`, `RecalcEditorTotal` |
| Screen | Noun, or Noun + `Detail` / `List` | `Customers`, `CustomerDetail` |
| Block | Noun describing the widget | `CustomerCard`, `HoursCalendar` |
| Role | PascalCase noun | `SalesManager` |
| Site property | PascalCase | `MaxUploadSizeMB` |
| Timer | `Timer_` + purpose | `Timer_SendReminders` |

### Action names

**Reusable server and client actions** (top-level actions under Logic, callable from anywhere): `<Entity>_<Verb>[<Qualifier>]`.

- `<Entity>` is the entity, structure or concept the action works on, in singular PascalCase: `Item`, `DaySheet`, `Calendar`. For utilities that don't belong to an entity, use the thing they act on: `Minutes_Format`, `Date_GetWeekStart`.
- `<Verb>` is one of `Get`, `GetById`, `GetList`, `Create`, `Update`, `CreateOrUpdate`, `Delete`, `Save`, `Clear`, `Validate`, `Format`, or another verb when none of those fits. Add a qualifier for variants: `Item_GetNewest`, `Item_GetByCode`, `Holiday_CreateIfMissing`.
- Exceptions: actions generated by the OutSystems templates (`DoLogin`, `DoLogout`) and the platform role functions (`Check<Role>Role`) keep their names. A timer's action may take the timer's purpose (`Bootstrap`).

**Screen and block actions bound to an event**: `<Event>_<Target>`.

| Event | Name | Example |
|---|---|---|
| Widget event (OnClick, OnChange, OnBlur, …) | `<Event>_<WidgetName>` | `OnClick_PreviousMonth`, `OnChange_HoursDropdown` |
| Same handler on several widgets | `<Event>_<Purpose>` | `OnClick_SaveDay` (Save as draft, Confirm day, Save day off) |
| Data action / aggregate On After Fetch | `OnAfterFetch_<DataSourceName>` | `OnAfterFetch_GetKPIs` |
| Block or screen event raised by a child block | `<EventName>_<BlockInstanceName>` | `OnDaySaved_HoursCalendar` |
| Lifecycle (OnInitialize, OnReady, OnRender, OnDestroy, OnParametersChanged) | the event name itself | `OnParametersChanged`, `OnReady` |

Screen and block actions that are not bound to an event (helpers called from other actions) use verb + noun: `OpenDayEditor`, `RecalcEditorTotal`. If an action is both bound to an event and called from other actions, name it for the event and move the shared logic into a helper.

## Data

- Entities that other modules read are **public with Read Only = Yes**. Writes go through public server actions in the Core module (`Customer_Create`, `Customer_Update`, …).
- Delete rules: `Protect` by default. Use `Delete` only for child records that have no meaning without the parent.
- Index the attributes used in filters on large tables.
- Store dates as Date Time in UTC. Convert for display in the UI.

## Logic

- Business rules live in server actions in Core, not in screen actions.
- Check permissions in the server action, not only on the screen. Screens can be bypassed.
- Raise user exceptions for business-rule violations, and catch them at the screen to show a feedback message.
- Keep client actions free of business logic. They validate input and call server actions or data actions.

## UI

- Use OutSystems UI patterns and blocks before custom HTML and CSS.
- App-wide CSS goes in the theme. Screen-specific CSS stays on the screen.
- Every screen has an explicit role check, or is marked Anonymous on purpose.

## Changes through the MCP

- One story per change set. Don't mix unrelated changes in a single review.
- Read before you write. Confirm an element's current state with the live read tools, not only with `snapshots/`.
- Lay out action flows before merging (see the `servicestudio-mcp-oml` skill).
- **No overlapping nodes** in any server, client, screen, block or data action flow. Two nodes overlap when their positions are less than 900 units apart both horizontally and vertically. The standard spacing is 1371 vertically and 1828 horizontally (`ConnectedBelow(node, 1371)`, `ToTheRightOf(node, 1828)`). Check every new or edited flow before merging; the query is in [`queries/overlapping-nodes.cs`](../queries/overlapping-nodes.cs) (run it as a throw-probe with `applyModelApiCode`, nothing is saved).
- Name every new action following [Action names](#action-names). A rename of an existing action is its own technical task, not part of an unrelated story.
